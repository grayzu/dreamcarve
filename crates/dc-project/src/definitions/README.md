## Versions

Each definition is a directory of versions, `<id>/v<n>.json`, compiled into
the binary. A project names one by `id` and `definition_version` and holds
only its own settings (ADR-0004, #106), so a released version is never
edited or removed: a project that names it must export the same bytes after
any upgrade.

- A change that changes emitted bytes is a new file, `<id>/v<n+1>.json`,
  added to `SOURCES` in `post_processor.rs`. New projects (`init`) and
  `export --post <id>` use the latest version; a project moves to it only
  when the user runs `export --post <id>`.
- Every file is pinned by hash in
  `post_processor::tests::released_definition_versions_are_unchanged`, so an
  edit in place fails CI. Pin a new version when it is added.
- The one edit made in place is a schema-wide field: every field of a
  definition is required, so when `PostProcessor` gains one, every released
  version gets it with the value that reproduces what it did before, and
  is re-pinned in the same change. Emitted bytes must not change, which
  `resolve_matches_old_embedded_definition` and the golden corpus check.
  #117 added `feed_speed.spindle_on_dwell.units` (`"seconds"` on both),
  `canned_cycles.reentry_gap_mm` (`null`; both have `canned_cycles: null`
  anyway) and the `default_settings.use_canned_cycles` setting (`false`)
  this way, and #283 `work_coordinates.machine_command` (`"G53"` on
  grblHAL and GRBL, `null` on the others; see "Machine-coordinate moves").
- #306 set LinuxCNC's `machine_command` to `"G53"` in place on both
  versions, re-pinned, once its documents and source were checked. That
  is allowed for the same reason: the field writes nothing unless a
  project sets `heights.tool_change_machine_z_mm`, which both versions
  refused before (`machine_z_needs_g53`), so no program either version
  could export changes. `emit::machine_command_writes_nothing_without_the_height`
  checks it on every version, and the goldens and corpus are unchanged.
- The checks in `dc-gcode`'s `post` tests (the controller facts below) run
  over every version of every definition.

A file is a `dc_project::PostProcessor` without the six fields a project
holds (`file_extension`, `feed_speed.spindle_control`,
`feed_speed.spindle_on_dwell.duration_s`, `tool_change.mode`,
`number_format.decimal_places`, `use_canned_cycles`), plus a
`default_settings` object with those six, under the names a project uses
(`file_extension`, `spindle_control`, `spindle_on_dwell_s`,
`tool_change_mode`, `decimal_places`, `use_canned_cycles`). A new project
starts from them. The test `bundled_definitions_validate` checks that every
file parses and has its id.

Version 1 of both is the definition a project embedded up to `.dcv` version
6, with the settings moved out and nothing else changed:
`post_processor::tests::resolve_matches_old_embedded_definition` compares
each, resolved with its default settings, with the old file, kept in
`tests/fixtures/post/`.

Rules for the emitter that come from the same check (enforced in `emit`, not
here): text substituted into comments (`{programName}`, `{toolName}`,
`{operationName}`) is reduced to printable ASCII without `( ) ; ! ? ~`,
since both controllers act on `!`, `~`, `?` and bytes above 0x7F even inside
comments, and `)` ends a comment early. Since #278 a non-ASCII character is
first transliterated by DreamCarve's own table (`dc-gcode/src/ascii.rs`:
Latin-1 Supplement, Latin Extended-A, the General Punctuation dashes, quotes
and dots, and `™`; "Café" → `Cafe`, "½" → `1/2`, "—" → `-`), and only a
character with no entry is dropped; no entry produces `( ) ; ! ? ~ { } %`,
which a test checks over every code point. This is an emitter rule, so it
applies to every definition version without a new one: it changes comment
bytes only, for names that hold such characters. On grblHAL, `!`, `?` and `~` inside a
comment act only while `legacy_rt_commands` (`$39`) is on, which is the
default (`DEFAULT_LEGACY_RTCOMMANDS On` in `config.h`; checked in
`protocol.c`), so they are still removed. Never emit M4 (needs a direction pin
or laser capability) or M7 (optional on both). Numbers never use exponent
notation. Arc IJ offsets are taken from the rounded start point emitted.

## Tool changes

There is no stop for the first tool. The user fits it and sets work zero
with it before starting the program, and `export` says so (#57). With
the project's `tool_change_mode` `"separate_programs"`, the default, a project with more
than one tool is one program per tool run (`emit_programs`, #95), and no
program changes tools. With `"m6"`, one program changes tools; that needs
a definition whose `tool_change.commands` has an `M6` line, which
validation checks, and otherwise `emit` fails with
`ExportError::ToolChangeNotSupported`, naming the tools. For a later tool
the program retracts to safe Z, stops the
spindle, and writes `T{n} M6 (MSG, Fit T{n} {name}. Set Z zero, then
resume.)` in place of the definition's `M6` line. Lines that only pause
(`M0`, `M1`) and `pause_after_change` are left out: one stop per change. A
new bit has a new length, so Z zero is set with it (#43). After the change
the program writes the setup again (the header's lines that only set modal
state, plus `G90`, units and work coordinates if the header leaves them
out, #55), writes its next motion and feed words in full, and retracts to
safe Z, measured from the new zero, before the spindle starts or the
router-on pause. A program that changes tools starts with `M61 Q<n>` for
its first tool. The safety pass accepts `M6` and `M61` only from a
definition with an `M6` line and mode `"m6"`, and checks `M6` as it checks
`M0`: at a
known Z at or above safe Z, Z unknown after it, setup required after it.

Checked on 2026-10-18 against `grblHAL/core` at commit
`4ec1ae44b857a70d2f9298344feac4b43ed0eb6b` (master that day):

- **Modes.** `$341` is the tool change mode: `Normal, Manual touch off,
  Manual touch off @ G59.3, Automatic touch off @ G59.3, Ignore M6`, 0 to 4
  (`settings.c` 2482). The help text for 0: "Normal: allows jogging for
  manual touch off. Set new position manually." (`settings.c` 2681).
- **`$341` must not be 4.** With no tool changer and mode 4, `M6` is
  dropped without a word (`gcode.c` 1845): no stop, so the program cuts
  with the old bit and the old Z zero. The post-processors chapter states
  this as a prerequisite; DreamCarve cannot read the setting at export.
- **Mode 0 stops without moving.** `tc_init` installs no tool-change
  handler for mode 0 or 4 (`tool_change.c` 563-566), so `M6` takes the
  manual branch: it syncs the planner, reports the line's `(MSG, ...)`
  (`gcode.c` 4229-4236), sets `EXEC_TOOL_CHANGE` and waits in
  `STATE_TOOL_CHANGE` (`gcode.c` 4262-4266). Jogging is allowed in that
  state (`system.c` 241), and cycle start resumes.
- **Modes 1 to 3 move the machine** (Z up; 2 and 3 also to a `G59.3` tool
  setter) and need homing first: Z for mode 1, X, Y and Z for 2 and 3
  (`tool_change.c` 459-462). They work, for users who set them up.
- **`M6` needs a stream that can be suspended.** Without
  `hal.stream.suspend_read` grblHAL rejects `M6` with
  `Status_GcodeUnsupportedCommand` (`error:20`, `gcode.c` 1846-1850). That
  failure is on the machine, not at export; the chapter documents it.
- **`M6` for the current tool is skipped** (`gcode.c` 2619-2621, "Tool
  already in spindle, ignore"), and the current tool survives a soft reset
  (`gcode.c` 794) and, with `tool_persistent`, a power cycle (`gcode.c`
  770-780). So the first tool has no `M6`, and a program that changes
  tools first sets the current tool with `M61 Q<n>` (`gcode.c` 1887-1889,
  2519). `M61` sets it at once, with no stop and no motion, when `<n>`
  differs from the pending tool (`gcode.c` 4155-4170), which after a reset
  is the current one (`gcode.c` 794). Without it, a later `T<n> M6` whose
  `<n>` was the last tool of the previous job would be skipped, and the
  program would cut with the wrong bit and Z zero.
- **The message goes on the `M6` line.** A comment-only line's message is
  reported when the line is parsed (`gcode.c` 1343-1346), which may be
  before the machine gets there. The message of the `M6` line is reported
  after the planner has synced (`gcode.c` 4229-4236).
- **GRBL 1.1 has no `M6`**: `grbl/gcode.c` lists it under unsupported, and
  the M-word `default` case fails with `STATUS_GCODE_UNSUPPORTED_COMMAND`.
  Its `M0` is a feed hold, in which `$J` jogging is refused
  (`grbl/system.c`: only in IDLE or JOG). So GRBL cannot stop for a new bit
  where the user can set Z zero, and `"m6"` is refused on it; one program
  per tool run works.

The tool-change height is the project's `heights.tool_change_machine_z_mm`
(#283; see "Machine-coordinate moves" below). Unset, as in every project
before format version 12, grblHAL waits in mode 0 at the clearance height,
or the operation's safe Z, and the user jogs up to swap the bit. Set, the
program rises to the clearance height in work coordinates, then writes
`G53 G0 Z<v>` before the `M5` and the `T<n> M6` (or, with manual spindle
control, before the router-off pause), and again before the footer.

## Machine-coordinate moves (`work_coordinates.machine_command`)

`work_coordinates.machine_command` is the non-modal command for one move
in machine coordinates, `G53`, or `null` (#283). It is a schema-wide field,
added in place to every released version and re-pinned ("Versions" above):
nothing writes it unless a project sets `heights.tool_change_machine_z_mm`,
so no version's bytes changed. #306 set it on LinuxCNC the same way. A definition with `null` refuses that height
(validation's `machine_z_needs_g53`, and `emit`); the safety pass refuses
every `G53` except S16's lift, and refuses that too unless the definition
documents `G53` and the project sets the height.

Where machine Z is. grblHAL and GRBL home Z to the top of its travel, at a
negative machine position, when Z homes upward (the default):

- grblHAL `machine_limits.c` 116-140 (`limits_set_work_envelope`): the
  homed envelope of an axis is `[max_travel + pulloff, −pulloff]`, with
  `pulloff` the homing pull-off when hard limits are on and 0 otherwise,
  and `max_travel` stored negative. Only `homing.flags.force_set_origin`
  with a downward-homing axis makes it positive.
- GRBL `grbl/limits.c` 382: an axis that homes upward is set to
  `−homing_pulloff` (0 with `HOMING_FORCE_SET_ORIGIN`), and
  `grbl/system.c` 348: soft limits accept `[max_travel, 0]`.

The exception, on both. GRBL built with `HOMING_FORCE_SET_ORIGIN` and Z
homing downward (its bit set in `$23`, `homing_dir_mask`) sets the homed
position to 0 and accepts `[0, −max_travel]`, a positive range
(`grbl/system.c` 340-344); grblHAL does the same with
`homing.flags.force_set_origin` and a downward-homing axis
(`machine_limits.c` 129-131). There Z 0 is the bottom of the travel, and
every negative machine Z is below it. Validation still requires a
negative value, so on such a machine no lift DreamCarve accepts is inside
the travel: it fails safe only with soft limits on, when the controller
refuses the target with an alarm before it moves: every line move, `G53`
included, goes through `limits_soft_check` (GRBL `motion_control.c`
34-38 and `limits.c` 411-430; grblHAL `motion_control.c` 96-99). With soft limits off it
would drive Z down toward the bottom switch, so the post-processors
chapter asks for soft limits on whenever a machine Z is set, and a
machine that homes Z downward cannot use the setting.

LinuxCNC (#306). Machine Z after homing is the configuration's `[JOINT_n]
HOME`, "The position that the joint will go to upon completion of the
homing sequence" (default 0), and the travel is `[AXIS_Z] MIN_LIMIT` to
`MAX_LIMIT` (INI configuration document,
<https://linuxcnc.org/docs/stable/html/config/ini-config.html>, sections
`[AXIS_<letter>]` and `[JOINT_<num>]`). Neither has a fixed sign, so the
check is of what LinuxCNC does with a value outside the travel, and of
where its own configuration tools put Z:

- **The configuration tools put Z 0 at the top.** Stepconf's defaults are
  Z travel −100 to 0 mm, or −4 to 0 in (`src/emc/usr_intf/stepconf/stepconf.py`
  474-476, 486-488), with home position 0 (388); pncconf's are the same
  (`src/emc/usr_intf/pncconf/data.py` 653, 753-754, 774-775). There every
  machine Z inside the travel is below 0, as on grblHAL and GRBL.
- **Not every configuration does.** The bundled simulator
  (`configs/sim/axis/axis_mm.ini` 152-156, 198-210) has Z travel −50.8 to
  101.6 mm with home 0, so its machine Z 0 is not the top, and a negative
  machine Z is a position inside the travel, possibly low. The chapter
  says to read the value off the machine's own Z in machine coordinates.
- **A program does not run on a machine that is not homed**, unless the
  configuration sets `[TRAJ] NO_FORCE_HOMING = 1`: `no_force_homing`
  defaults to 0 (`src/emc/task/emctaskmain.cc` 121), and running a
  program then fails with "Can't run a program when not homed"
  (2302-2303). The INI document: "The default behavior is for LinuxCNC
  to force the user to home the machine before any MDI command or a
  program is run."
- **Once homed, the soft limits always apply**, with no setting to turn
  them off ("The axis must be homed before MIN_LIMIT is in force", INI
  document), and a line move whose end is outside them is refused before
  it is queued: `EMCMOT_SET_LINE` (`src/emc/motion/command.c` 1011-1025)
  calls `inRange`, which reports "%s move on line %d would exceed %c's %s
  limit" (191-226), then aborts the trajectory and sets the motion
  error. A `G53 G0` is such a move.

So on LinuxCNC a machine Z outside the travel stops the program before
the lift, on every configuration that forces homing, the default. A
configuration whose Z travel is all at or above 0 cannot use the
setting, since validation refuses every value inside it: that fails safe.
Validation and S16 keep the rule of grblHAL and GRBL, below 0 as written,
with no rule of their own for LinuxCNC.

The modal state at a LinuxCNC lift. The header sets `G90`, `G40` and
`G80`, and every pause sets them again (#55), so none of `G53`'s errors
applies: not incremental (`interp_check.cc` 105-108), not with cutter
compensation (`interp_convert.cc` 4855-4857), and the lift's own `G0`
is the motion `G53` needs (`interp_check.cc` 104-105), after the `G80`
that ends a series of canned cycles. `G20` and `G21` both work (the
table above). LinuxCNC's definition has no `M6` ("LinuxCNC" below), so
`"m6"` is refused there and the lift is written only before the footer
`M5`, `M2`, or, with manual spindle control, before the router-off
`M0`, which only pauses ([M] `#mcode:m0-m1`).

So `tool_change_machine_z_mm` must be below 0 as the program writes it:
validation refuses 0 or more, and a value that rounds to 0 in the
program's decimal places (`machine_z_not_below_home`), and the
post-processors chapter says to stay at least the pull-off below 0.
Machine coordinates mean nothing on a machine that is not homed, which
DreamCarve cannot check, so `export` says to home it whenever a program
has a lift, and the program says so in a header comment in the
definition's comment syntax, `( Lifts to machine Z with G53: home the
machine before running. Needs Z to home upward, or soft limits on with
$20=1 )` (`;` on GRBL v3). Both name soft limits (#308), since a user who
never reads the post-processors chapter would not otherwise learn that
on a machine that homes Z downward the lift is safe only with them on.
DreamCarve cannot read the homing direction or `$20`, so this is a note,
not a refusal. The comment holds no `( ) ;`, and its `$` is not a command:
both controllers read `$` as a system command only as the first character
of a line (GRBL `grbl/protocol.c` 96, grblHAL `protocol.c` 249), and the
line starts with the comment.

What DreamCarve writes, the safety pass's S16: `G53 G0 Z<v>`, alone on its
line, in the program's units, after a retract in work coordinates to at
least safe Z and at the XY where the bit already is; only before a
tool-change stop or before the footer. With manual spindle control the
router-off pause follows the lift, and the user may jog there, so the
program lifts again right before `T<n> M6`: S16 accepts a lift right
after a stop that followed a lift, with nothing moved between, once the
units are set again. After it work Z is unknown, so the
next move in XY needs a retract in work coordinates first, as after a
pause (S4). Any XY move (the park point) comes before the lift, at a work
Z the safety pass checks, never after it. The footer stays without `G53`
(see "Verification": `G0 G53 Z0` was removed from grblHAL's footer, since
machine Z 0 is past the limit with soft limits on).

### Mach3, UCCNC and generic: refused (#306)

`G53` is enabled only where its documents prove all four points: it is
non-modal and moves in machine coordinates with `G0`, ignoring the work,
`G92` and tool length offsets (or naming the ones that apply); which
machine Z values are valid after homing; that it is allowed in the
program's modal state at that point; and how it meets the tool change.
These three do not, so their `machine_command` stays `null`, and
`check` and `export` refuse `tool_change_machine_z_mm` there
(`machine_z_needs_g53`).

- **Mach3** ([MILL], *Using Mach3Mill* 1.84, cited under "Mach3" below).
  10.7.17 "Move in Absolute Coordinates - G53" (p. 10-23, 10-24) gives
  `G0 G53 Z~`, "G53 is not modal", and the errors without `G0`/`G1` and
  with cutter compensation; 10.4.3 (p. 10-9) and figure 10.3 put it in
  group 0. But:
  - Nothing says which offsets a `G53` move ignores. It moves "to a
    point expressed in absolute coordinates", and the manual's absolute
    coordinates are those "of the controlled point" (7.2.1, p. 7-3),
    which "can be moved out along the spindle axis by specifying some
    positive amount for the tool length offset" (10.1.4, p. 10-4). So a
    `G53 Z` may place the bit's tip, with the offset, not the spindle:
    with the Tool Offset On/Off toggle on (7.3.1, p. 7-5), the spindle
    would stop the offset higher than the value, past the top of the
    travel if the offset is larger than the gap, or lower with a negative
    offset (10.7.14, p. 10-23, provides `G44` for negative table entries).
    A forum report, not evidence, describes a `G53 Z` going higher with an
    offset set (<https://www.machsupport.com/forum/index.php/topic,23124.10.html>).
  - Machine Z after homing is a setting. 7.2.2 (p. 7-4): machine zero is
    set to given values, "frequently 0.0", and "The Z home switch is
    generally set at the highest Z position"; with Auto Zero the DRO is set
    to the Home Off. value instead (5.6.1.2, p. 5-18).
  - Soft limits apply "only when switched on using the Software Limits
    toggle button" (5.6.1.3, p. 5-19), and nothing in the manual stops a
    program on a machine that was not referenced.
  - 10.1.10 (p. 10-6) warns to "check very carefully the system's
    response to changing units while tool and fixture offsets are
    loaded", and 10.7.10 (p. 10-20) keeps `G28`'s home "in unspecified
    length units", so the inch lift is not proven either.

  The Mach3 wiki returned HTTP 500 again on 2026-10-21.
- **UCCNC** ([UM], manual 1.0047, cited under "UCCNC" below). 4.1.1 "Move
  in Machine Coordinates : G53" (p. 58-59) gives `G1 G53 X… Y… Z…` "(or
  use G0 instead of G1)", "G53 is not modal", and the error without
  `G0`/`G1`; the modal group table (p. 50) puts it in group 0. But:
  - Nothing says what a `G53` move does with the tool offset. 3.10
    "Offsets" (p. 42-43) has "the Current coordinates which is the Machine
    coordinates substracted with the Work offsets" and a separate "Tool
    offset", and "Clearing the tool offset adds the tool offset to the
    Current coordinates".
  - Nor with scaling: `G51` scales "All motion commands including linear
    and circular motion commands", and "In case of negative scale factors
    the axis gets mirrored" (p. 58), while `G68` rotation says it rotates
    "all of the motion commands ..., except the movements in the absolute
    coordinate system (G53)" (p. 59). A `G51 Z` left set would scale, or
    flip, the lift.
  - Machine Z after homing is a setting: "Write offset on Homing ...
    sets the coordinate to write to the axis position DRO when a homing
    action is executed", and the homing direction is the "Direction
    positive" checkbox (3.1, p. 17). There is no convention to check a
    value against.
  - Soft limits are optional ("Enable softlimits", 3.6, p. 35), and
    when on the axis stops when "the softlimits coordinate is reached"
    (p. 40), rather than the move being refused before it starts.
- **Generic** ([NIST] 3.5.12 defines `G53`; 3.2.2 the absolute
  coordinate system). The definition is for controllers that are not
  listed, so there is no controller whose homing, machine Z or offsets
  could be checked. It stays `null` for good.

## Manual spindle control

With the project's `spindle_control: "manual"` the program sends no `M3`, `M5`
or `S` word. After any tool change (see "Tool changes" above) it
pauses with
`M0 (MSG, Turn the router ON. Speed {rpm} RPM. Resume to start cutting.)`
before each tool's first cut, and retracts to safe Z and pauses with
`M0 (MSG, Turn the router OFF.)` before a tool change and at the end. With `"m6"`, a later
tool has two stops before it cuts, `M6` and the router-on pause, with a
retract between them: the router
starts only after the bit has been lifted from the Z zero the user set.
Checked on
2026-10-16 against each controller's source:

- **The pause is reliable on both.** `M0` syncs the planner
  (`protocol_buffer_synchronize`), then enters feed hold, and resumes only on
  cycle start (`~` or the sender's Resume button). GRBL `grbl/gcode.c`,
  "[21. Program flow]" (`EXEC_FEED_HOLD`); grblHAL `gcode.c`, the same
  section (`ProgramFlow_Paused`). So the pause is always `M0`, never the
  definition's `pause_command`: `M1` is an optional stop the controller may
  skip.
- **The message is not.** GRBL has no message support: its `gcode.c` says
  "[1. Comments ]: MSG's NOT SUPPORTED. Comment handling performed by
  protocol.", and the comment is stripped before parsing. The user sees the
  text only if the sender shows the line it paused on. grblHAL turns a
  `(MSG, text)` comment into a `[MSG:text]` report to the sender
  (`gcode.c`, `gc_output_message`), unless the driver disables message
  handling. So the message is written as a `( )` comment in both dialects,
  even where the definition's comments are `;`: grblHAL reports it, and GRBL
  ignores it harmlessly.
- How each sender (gSender, UGS, CNCjs, ioSender) shows an `M0` pause and
  its message is not verified; #17 checks it on a real machine. Because the
  message may not be shown, `Program::pauses` lists every pause with its line
  and message for the CLI to print.

Sources:

- GRBL v1.1: `gnea/grbl` `README.md`, `grbl/gcode.c`, `grbl/serial.c`,
  `grbl/protocol.c`, `grbl/config.h`, `grbl/system.c`; wiki pages "Grbl
  v1.1 Commands", "Grbl v1.1 Interface", "Grbl v1.1 Configuration".
- grblHAL: `grblHAL/core` `gcode.c`, `grbl.h`, `config.h`, `protocol.c`,
  `machine_limits.c`, `tool_change.c`, `settings.c`, `system.c`; wiki pages
  "Manual, semi-automatic and automatic tool change", "Manual tool change
  protocol", "Changes from grbl 1.1".

Still needs a check on a real machine: the sender's handling of comments,
`$32` laser mode off, `$30` at or above the requested RPM, and spindle
spin-up time: the bundled 3 s dwell may be too short for a large spindle or
VFD ramp; raise `spindle_on_dwell_s` in the project if so.

## Comments on grblHAL and GRBL (`grblhal/v2.json`, `grbl/v2.json`)

Version 1 opens the program with `( {programName} )` (grblHAL) and
`; {programName}` (GRBL), so the project name, which is user text, is the
first thing in a comment. Version 2 is version 1 with that one line
changed to `( Project: {programName} )` and `; Project: {programName}`,
as on the slice 17 definitions (see the rules below). It is a new version,
not an edit, because it changes emitted bytes ("Versions" above). A
project that names version 1 keeps it until the user runs
`export --post <id>`.

Checked on 2026-10-21 against `grblHAL/core` at commit
`4ec1ae44b857a70d2f9298344feac4b43ed0eb6b` (master that day) and
`gnea/grbl` at `bfb67f0c7963fe3ce4aaf8a97f9009ea5a8db36e` (master, v1.1h):

- **grblHAL acts on four comment keywords.** `gc_normalize_block`
  (`gcode.c` 1098-1175) passes the text of each `( )` comment to
  `grbl.on_process_gcode_comment` (1141), then checks it for `MSG,`
  (1146, reported to the sender), then passes it to
  `grbl.on_gcode_comment` (1160). With expressions enabled
  (`NGC_EXPRESSIONS_ENABLE`), the first hook is `ngc_process_comment`
  (`grbllib.c` 281), which acts on `DEBUG,` and `PRINT,` (`ngc_expr.c`
  1087, 1093), and `ngc_flowctrl_init` (`gcode.c` 851) installs a second
  hook that on `ABORT,` reports the text as an error and returns
  `Status_UserException`, which stops the program (`ngc_flowctrl.c`
  356-366, 379-380). A plugin may hook either function as well.
- **Each check is a case-insensitive prefix match on the comment's text,
  with no whitespace skipped** (`strncasecmp(comment, ...)`). The line
  reader strips only leading whitespace and control characters
  (`protocol.c` 292-293), so the space after `(` reaches the checks. So
  grblHAL's own checks do not match a version 1 header, `( MSG, x )`,
  whose text starts with a space; a plugin that trims the text might.
  Version 2 does not rely on that space: its comment text starts with
  `Project:`, which is none of the keywords, whatever the name.
- **A `;` comment is never interpreted by grblHAL.** A line whose first
  character is `;` is dropped before any comment is looked at (`gcode.c`
  1106-1109), and a later `;` ends the line (1120-1124). So
  `; Project: {programName}` does nothing on grblHAL, which runs GRBL
  programs too.
- **GRBL 1.1 interprets no comment.** Its line reader throws away every
  character inside `( )` and after `;` (`grbl/protocol.c` 113-133), and
  `grbl/gcode.c` says "MSG's NOT SUPPORTED". The GRBL change keeps the two
  dialects alike and the rule checked by one test.
- `:` is not a real-time command on either controller, so the new text
  adds nothing the emitter has to filter.

`post::user_text_never_starts_a_comment` checks the latest version of
every definition; `post::grbl_v2_project_comment_opens_with_fixed_text`
checks that version 2 differs from version 1 only in that line.

## Rules for the slice 17 definitions

LinuxCNC, Mach3, UCCNC and generic were checked on 2026-10-20 and
2026-10-21, line by line, against each controller's own documentation or
source (`AGENTS.md`, "Reference implementation"), then against the safety
rules. PureCutCNC's file was the starting point, not the evidence. Where a
document is silent or ambiguous, the definition takes the conservative
setting: plain moves rather than a canned cycle, and no `M6`.

Choices that apply to all four:

- **No `M6`, so `"m6"` mode is refused.** DreamCarve's `"m6"` program
  stops at `T<n> M6` and asks the user to fit the bit and set Z zero
  (#43, #57). No new controller documents a stop where the user can do
  that: see each section. Each tool run is a program of its own instead
  (`"separate_programs"`, #95). Each definition's tool change is `M5`,
  `M0`. It is never written: `emit` refuses a second tool in one program
  on a definition without `M6`.
- **No `G43 H`, and since version 2 no `G49`.** A tool length offset needs
  a tool table DreamCarve does not write. The user sets Z zero with each
  bit, as on grblHAL. Version 1 of each header cancelled any offset with
  `G49`; version 2 leaves the offset alone, because the zero the user set
  includes it (see "Tool length offset at touch-off", and for grblHAL and
  GRBL "Header modal state").
- **User text never opens a comment.** LinuxCNC acts on a comment that
  starts with a keyword: `(MSG,`, `(DEBUG,`, `(PRINT,`, `(LOG,`,
  `(LOGOPEN,file)`, which truncates the file, and `(PROBEOPEN file)`
  (LinuxCNC G-code overview, sections "Messages", "Probe Logging",
  "Logging", "Debug Messages", "Print Messages",
  <https://linuxcnc.org/docs/stable/html/gcode/overview.html#gcode:messages>).
  A project named `LOGOPEN,x` would otherwise write `( LOGOPEN,x )`. So
  the first header comment is `( Project: {programName} )`, not
  `( {programName} )`. `post::user_text_never_starts_a_comment` checks it
  on the latest version of every definition. grblHAL and GRBL got the same
  header in version 2 (#171; see "Comments on grblHAL and GRBL").
- **`(MSG, ...)` pauses.** DreamCarve's manual-spindle pauses are
  `M0 (MSG, ...)`. LinuxCNC and Mach3 show the message. UCCNC documents no
  `MSG`; RS274/NGC says messages "should be displayed" (3.3.4). Where the
  message is not shown, `export` still lists every pause.
- **Header modal codes.** `G40` and `G80` (and, in version 1, `G49`)
  only cancel modes DreamCarve never sets. `G91.1` selects incremental arc centres, which is
  how DreamCarve writes `I` and `J`. The safety pass accepts all four in
  any program, and `G90.1` in none (#154). Each line of the header is
  written again after every pause, with the units and WCS lines (#55).

## Tool length offset at touch-off (version 2 of LinuxCNC, Mach3, UCCNC)

The #73 review found that on grblHAL and GRBL the work zero a user sets
with `G10 L20` includes the active tool length offset, so `G49` at program
start would move every Z by it. Those headers never had `G49`. The
question for LinuxCNC, Mach3 and UCCNC, whose version 1 headers have it
(#286): if the user sets Z zero while an offset is active, does `G49`
move Z relative to that zero? Each was checked on 2026-10-21. The rule
was conservative: unless the documentation shows `G49` is harmless there,
it is removed.

- **LinuxCNC: it moves Z.** The documentation does not say. The G-code
  reference, `#gcode:g10-l20`, says only that `G10 L20` sets the offset
  "to a calculated value that makes the current coordinates become the
  given value". `#gcode:g49` says only that `G49` "cancels tool length
  compensation". The tool compensation page,
  <https://linuxcnc.org/docs/stable/html/gcode/tool-compensation.html>,
  "Touch Off", is silent on an offset already in effect. The interpreter
  source on branch `2.9`, at `a33293f46575c809e082e0806e79ab996f982513`,
  settles it:
  - `interp_convert.cc` L2447 gives the machine position as
    `current_z + axis_offset_z + origin_offset_z + tool_offset.tran.z`.
  - `G10 L20` (L4263, L4325) takes `cz` from `find_current_in_system`
    (`interp_find.cc` L467-510), which starts from `current_z`, the
    position with the tool offset already taken out. It does not use
    `find_current_in_system_without_tlo`, which `G10 L10`/`L11` use
    (L4030). So the new G5x Z is machine Z − offset − G92 − the given
    value.
  - AXIS's Touch Off sends exactly that `G10 L20`
    (`src/emc/usr_intf/axis/scripts/axis.py` L2790).
  - `G49` sets the offset to 0 and adds the old one to `current_z`
    (`interp_convert.cc` L5793).

  From then on, every programmed Z is reached with the tip one offset
  lower than the zero the user touched off, when the offset is positive.
  `M2` does not reset `G43`/`G49` ([M] `#mcode:m2-m30` lists what it
  resets), so an offset applied by a tool-setter routine or MDI is still
  active when the program starts.
- **Mach3: it moves Z, and the manual does not say otherwise.**
  *Using Mach3Mill* 1.84 (above, [MILL]):
  - 10.1.4 "Controlled Point" (p. 10-4): the point is moved "out along
    the spindle axis by specifying some positive amount for the tool
    length offset".
  - 7.2.1 (p. 7-3): "The work offset values are always added [to] the
    numbers in the axis DROs (i.e. the current coordinates of the
    controlled point) to give the absolute machine coordinates". Zeroing
    an axis DRO updates the work offset "so the controlled point is
    referred to by the value now in the axis DRO" (p. 7-4).
  - 6.2.11.1 (p. 6-10): Set Z "will set up the Z value of the current
    work offset so that the tool is at the given height".
  - 7.3.1 (p. 7-5): with a tool's offset switched on, "the Z axis DRO
    will read 0.0", and the offsets are switched on and off "in the part
    program (T word, M6, G43 and G49)".
  - 10.1.11 (p. 10-6): the current position numbers are adjusted, with
    no motion, when the "Tool length offset is changed".

  So a zero set with the Tool Offset On/Off toggle on includes the
  offset, and `G49` moves the controlled point back by it. 6.6.2 still
  advises a program to include `G49`, and 10.7.14 says only "To use no
  tool length offset, program G49". Neither says it is safe after such
  a zero.
- **UCCNC: the manual does not establish it is harmless.** [UM] (below):
  - 3.10 "Offsets" (p. 42-43): the "Tool offset ... is the tool length
    compensation", and "Clearing the tool offset adds the tool offset to
    the Current coordinates", so the current coordinates include it.
  - 3.11.1 (p. 43): "The tool offset can be cleared programming G49".
  - 4.1.1 "Tool Length Offsets : G43, G44 and G49" (p. 57-58): "To
    cancel the tool length offset compensation, program G49."
  - 4.3.4 and 4.3.5 (p. 72): the axis zero buttons and the offsets.

  The manual does not say whether zeroing an axis with a tool offset in
  force takes the offset into account. If it does, as the current
  coordinates do, `G49` moves Z by the offset.

So version 2 of each is version 1 with `G49` removed from the header
line, and nothing else changed (`post::linuxcnc_v2_header_has_no_g49`,
`mach3_v2_…`, `uccnc_v2_…`). No line of any definition sets an offset
(`post::no_definition_has_g43`), and version 2 has no `G44` or `G49`
either. So the offset in force when the user set Z zero, if any, stays
in force for the whole program, and the zero means what it meant at
touch-off. `G40` and `G80` stay: they cancel modes DreamCarve never uses,
and neither affects where Z is. A project that names version 1 keeps it,
byte for byte, until `export --post <id>`
(`cli::linuxcnc_v1_project_still_exports_byte_identically`).

Not used, and why:

- **`%`.** [O] "File Requirements": a percent line "is optional if the
  file has an M2 or M30 in it", and "an error will be signaled if a file
  has a percent line at the beginning but not at the end". The program ends
  with `M2`.
- **`M6`.** With `hal_manualtoolchange`, `M6` stops the spindle and "the
  dialog will stay active until the 'continue' button is pressed" ([TC]).
  Nothing documents jogging or touching off while it waits, and LinuxCNC's
  answer to a new bit's length is `G43` with a tool table ([M]
  `#mcode:m6`: "The tool length offset is not changed by M6, use G43 after
  the M6"). Without a tool changer component, the stepper configuration's
  HAL loops `iocontrol.0.tool-change` back to `tool-changed`
  (<https://linuxcnc.org/docs/stable/html/config/stepper.html#_standard_pinout_hal>),
  so `M6` returns at once and the program would cut with the old bit. And
  `T<n>` must be in the tool table. So no `M6`; one program per tool run.

| `M0` (tool change, never written) | [NIST] 3.6.1: "To stop a running program temporarily (regardless of the setting of the optional stop switch), program M0." | |
| `M30` | [NIST] 3.6.1: "To exchange pallet shuttles and then end a program, program M30." Both `M2` and `M30` reset the modes and stop the spindle. | PureCutCNC's choice, and what most controllers expect. |

| File extension `nc` | none | The usual extension for G-code. |

Not used: `%` (optional with `M30`, [NIST] 3.1), line numbers (optional,
