## Versions

Each definition is a directory of versions, `<id>/v<n>.json`, compiled into
the binary. A project names one by `id` and `definition_version` and holds
only its own settings (ADR-0004, #106), so a released version is never
edited or removed: a project that names it must export the same bytes after
any upgrade.

- A change that changes emitted bytes is a new file, `<id>/v<n+1>.json`,
  added to `SOURCES` in `post_processor.rs`. New projects (`init`) and
  `export --post <id>` use the latest version; a project moves to it only
  when the user runs `export --post <id>`.
- Every file is pinned by hash in
  `post_processor::tests::released_definition_versions_are_unchanged`, so an
  edit in place fails CI. Pin a new version when it is added.
- The one edit made in place is a schema-wide field: every field of a
  definition is required, so when `PostProcessor` gains one, every released
  version gets it with the value that reproduces what it did before, and
  is re-pinned in the same change. Emitted bytes must not change, which
  `resolve_matches_old_embedded_definition` and the golden corpus check.
  #117 added `feed_speed.spindle_on_dwell.units` (`"seconds"` on both),
  `canned_cycles.reentry_gap_mm` (`null`; both have `canned_cycles: null`
  anyway) and the `default_settings.use_canned_cycles` setting (`false`)
  this way.
- The checks in `dc-gcode`'s `post` tests (the controller facts below) run
  over every version of every definition.

A file is a `dc_project::PostProcessor` without the six fields a project
holds (`file_extension`, `feed_speed.spindle_control`,
`feed_speed.spindle_on_dwell.duration_s`, `tool_change.mode`,
`number_format.decimal_places`, `use_canned_cycles`), plus a
`default_settings` object with those six, under the names a project uses
(`file_extension`, `spindle_control`, `spindle_on_dwell_s`,
`tool_change_mode`, `decimal_places`, `use_canned_cycles`). A new project
starts from them. The test `bundled_definitions_validate` checks that every
file parses and has its id.

Version 1 of both is the definition a project embedded up to `.dcv` version
6, with the settings moved out and nothing else changed:
`post_processor::tests::resolve_matches_old_embedded_definition` compares
each, resolved with its default settings, with the old file, kept in
`tests/fixtures/post/`.

## Modifications

These files were modified from the upstream copies (Apache-2.0 §4(b)):

- Keys are converted from camelCase to snake_case (`fileExtension` →
  `file_extension`, `spindleOnCW` → `spindle_on_cw`), because `.dcv` keys
  are snake_case (`docs/rust-guidelines.md`, "Serialization").
- `"vendor": null` is added, since every field is required and `Option`
  fields are written as `null`.
- The header line `Generated by PureCutCNC on {date}` reads
  `Generated by DreamCarve on {date}`.
- The fields a project sets are moved into `default_settings` (#106; see
  "Versions" above).
- The safety and correctness changes listed under "Verification" below,
  and, for the four later files, under "Changed from PureCutCNC" in each
  one's section.

Values are otherwise unchanged. `{placeholder}` tokens such as
`{programName}` and `{date}` are template tokens filled at export, not keys,
so they keep their upstream spelling.

Rules for the emitter that come from the same check (enforced in `emit`, not
here): text substituted into comments (`{programName}`, `{toolName}`,
`{operationName}`) is reduced to printable ASCII without `( ) ; ! ? ~`,
since both controllers act on `!`, `~`, `?` and bytes above 0x7F even inside
comments, and `)` ends a comment early. On grblHAL, `!`, `?` and `~` inside a
comment act only while `legacy_rt_commands` (`$39`) is on, which is the
default (`DEFAULT_LEGACY_RTCOMMANDS On` in `config.h`; checked in
`protocol.c`), so they are still removed. Never emit M4 (needs a direction pin
or laser capability) or M7 (optional on both). Numbers never use exponent
notation. Arc IJ offsets are taken from the rounded start point emitted.

## Tool changes

There is no stop for the first tool. The user fits it and sets work zero
with it before starting the program, and `export` says so (#57). With
the project's `tool_change_mode` `"separate_programs"`, the default, a project with more
than one tool is one program per tool run (`emit_programs`, #95), and no
program changes tools. With `"m6"`, one program changes tools; that needs
a definition whose `tool_change.commands` has an `M6` line, which
validation checks, and otherwise `emit` fails with
`ExportError::ToolChangeNotSupported`, naming the tools. For a later tool
the program retracts to safe Z, stops the
spindle, and writes `T{n} M6 (MSG, Fit T{n} {name}. Set Z zero, then
resume.)` in place of the definition's `M6` line. Lines that only pause
(`M0`, `M1`) and `pause_after_change` are left out: one stop per change. A
new bit has a new length, so Z zero is set with it (#43). After the change
the program writes the setup again (the header's lines that only set modal
state, plus `G90`, units and work coordinates if the header leaves them
out, #55), writes its next motion and feed words in full, and retracts to
safe Z, measured from the new zero, before the spindle starts or the
router-on pause. A program that changes tools starts with `M61 Q<n>` for
its first tool. The safety pass accepts `M6` and `M61` only from a
definition with an `M6` line and mode `"m6"`, and checks `M6` as it checks
`M0`: at a
known Z at or above safe Z, Z unknown after it, setup required after it.

Checked on 2026-10-18 against `grblHAL/core` at commit
`4ec1ae44b857a70d2f9298344feac4b43ed0eb6b` (master that day):

- **Modes.** `$341` is the tool change mode: `Normal, Manual touch off,
  Manual touch off @ G59.3, Automatic touch off @ G59.3, Ignore M6`, 0 to 4
  (`settings.c` 2482). The help text for 0: "Normal: allows jogging for
  manual touch off. Set new position manually." (`settings.c` 2681).
- **`$341` must not be 4.** With no tool changer and mode 4, `M6` is
  dropped without a word (`gcode.c` 1845): no stop, so the program cuts
  with the old bit and the old Z zero. The post-processors chapter states
  this as a prerequisite; DreamCarve cannot read the setting at export.
- **Mode 0 stops without moving.** `tc_init` installs no tool-change
  handler for mode 0 or 4 (`tool_change.c` 563-566), so `M6` takes the
  manual branch: it syncs the planner, reports the line's `(MSG, ...)`
  (`gcode.c` 4229-4236), sets `EXEC_TOOL_CHANGE` and waits in
  `STATE_TOOL_CHANGE` (`gcode.c` 4262-4266). Jogging is allowed in that
  state (`system.c` 241), and cycle start resumes.
- **Modes 1 to 3 move the machine** (Z up; 2 and 3 also to a `G59.3` tool
  setter) and need homing first: Z for mode 1, X, Y and Z for 2 and 3
  (`tool_change.c` 459-462). They work, for users who set them up.
- **`M6` needs a stream that can be suspended.** Without
  `hal.stream.suspend_read` grblHAL rejects `M6` with
  `Status_GcodeUnsupportedCommand` (`error:20`, `gcode.c` 1846-1850). That
  failure is on the machine, not at export; the chapter documents it.
- **`M6` for the current tool is skipped** (`gcode.c` 2619-2621, "Tool
  already in spindle, ignore"), and the current tool survives a soft reset
  (`gcode.c` 794) and, with `tool_persistent`, a power cycle (`gcode.c`
  770-780). So the first tool has no `M6`, and a program that changes
  tools first sets the current tool with `M61 Q<n>` (`gcode.c` 1887-1889,
  2519). `M61` sets it at once, with no stop and no motion, when `<n>`
  differs from the pending tool (`gcode.c` 4155-4170), which after a reset
  is the current one (`gcode.c` 794). Without it, a later `T<n> M6` whose
  `<n>` was the last tool of the previous job would be skipped, and the
  program would cut with the wrong bit and Z zero.
- **The message goes on the `M6` line.** A comment-only line's message is
  reported when the line is parsed (`gcode.c` 1343-1346), which may be
  before the machine gets there. The message of the `M6` line is reported
  after the planner has synced (`gcode.c` 4229-4236).
- **GRBL 1.1 has no `M6`**: `grbl/gcode.c` lists it under unsupported, and
  the M-word `default` case fails with `STATUS_GCODE_UNSUPPORTED_COMMAND`.
  Its `M0` is a feed hold, in which `$J` jogging is refused
  (`grbl/system.c`: only in IDLE or JOG). So GRBL cannot stop for a new bit
  where the user can set Z zero, and `"m6"` is refused on it; one program
  per tool run works.

The tool-change height is not set: in mode 0 grblHAL waits at the
operation's safe Z, and the user jogs up to swap the bit (#73).

## Manual spindle control

With the project's `spindle_control: "manual"` the program sends no `M3`, `M5`
or `S` word. After any tool change (see "Tool changes" above) it
pauses with
`M0 (MSG, Turn the router ON. Speed {rpm} RPM. Resume to start cutting.)`
before each tool's first cut, and retracts to safe Z and pauses with
`M0 (MSG, Turn the router OFF.)` before a tool change and at the end. With `"m6"`, a later
tool has two stops before it cuts, `M6` and the router-on pause, with a
retract between them: the router
starts only after the bit has been lifted from the Z zero the user set.
Checked on
2026-10-16 against each controller's source:

- **The pause is reliable on both.** `M0` syncs the planner
  (`protocol_buffer_synchronize`), then enters feed hold, and resumes only on
  cycle start (`~` or the sender's Resume button). GRBL `grbl/gcode.c`,
  "[21. Program flow]" (`EXEC_FEED_HOLD`); grblHAL `gcode.c`, the same
  section (`ProgramFlow_Paused`). So the pause is always `M0`, never the
  definition's `pause_command`: `M1` is an optional stop the controller may
  skip.
- **The message is not.** GRBL has no message support: its `gcode.c` says
  "[1. Comments ]: MSG's NOT SUPPORTED. Comment handling performed by
  protocol.", and the comment is stripped before parsing. The user sees the
  text only if the sender shows the line it paused on. grblHAL turns a
  `(MSG, text)` comment into a `[MSG:text]` report to the sender
  (`gcode.c`, `gc_output_message`), unless the driver disables message
  handling. So the message is written as a `( )` comment in both dialects,
  even where the definition's comments are `;`: grblHAL reports it, and GRBL
  ignores it harmlessly.
- How each sender (gSender, UGS, CNCjs, ioSender) shows an `M0` pause and
  its message is not verified; #17 checks it on a real machine. Because the
  message may not be shown, `Program::pauses` lists every pause with its line
  and message for the CLI to print.

Sources:

- GRBL v1.1: `gnea/grbl` `README.md`, `grbl/gcode.c`, `grbl/serial.c`,
  `grbl/protocol.c`, `grbl/config.h`, `grbl/system.c`; wiki pages "Grbl
  v1.1 Commands", "Grbl v1.1 Interface", "Grbl v1.1 Configuration".
- grblHAL: `grblHAL/core` `gcode.c`, `grbl.h`, `config.h`, `protocol.c`,
  `machine_limits.c`, `tool_change.c`, `settings.c`, `system.c`; wiki pages
  "Manual, semi-automatic and automatic tool change", "Manual tool change
  protocol", "Changes from grbl 1.1".

Still needs a check on a real machine: the sender's handling of comments,
`$32` laser mode off, `$30` at or above the requested RPM, and spindle
spin-up time: the bundled 3 s dwell may be too short for a large spindle or
VFD ramp; raise `spindle_on_dwell_s` in the project if so.

## Rules for the slice 17 definitions

LinuxCNC, Mach3, UCCNC and generic were checked on 2026-10-20 and
2026-10-21, line by line, against each controller's own documentation or
source (`AGENTS.md`, "Reference implementation"), then against the safety
rules. PureCutCNC's file was the starting point, not the evidence. Where a
document is silent or ambiguous, the definition takes the conservative
setting: plain moves rather than a canned cycle, and no `M6`.

Choices that apply to all four:

- **No `M6`, so `"m6"` mode is refused.** DreamCarve's `"m6"` program
  stops at `T<n> M6` and asks the user to fit the bit and set Z zero
  (#43, #57). No new controller documents a stop where the user can do
  that: see each section. Each tool run is a program of its own instead
  (`"separate_programs"`, #95). Each definition's tool change is `M5`,
  `M0`. It is never written: `emit` refuses a second tool in one program
  on a definition without `M6`.
- **No `G43 H`.** A tool length offset needs a tool table DreamCarve does
  not write. The user sets Z zero with each bit, as on grblHAL. The
  headers cancel any offset with `G49` where the controller documents it.
- **User text never opens a comment.** LinuxCNC acts on a comment that
  starts with a keyword: `(MSG,`, `(DEBUG,`, `(PRINT,`, `(LOG,`,
  `(LOGOPEN,file)`, which truncates the file, and `(PROBEOPEN file)`
  (LinuxCNC G-code overview, sections "Messages", "Probe Logging",
  "Logging", "Debug Messages", "Print Messages",
  <https://linuxcnc.org/docs/stable/html/gcode/overview.html#gcode:messages>).
  A project named `LOGOPEN,x` would otherwise write `( LOGOPEN,x )`. So
  the first header comment is `( Project: {programName} )`, not
  `( {programName} )`. `post::user_text_never_starts_a_comment` checks it.
  grblHAL's and GRBL's released files still start a comment with the name.
- **`(MSG, ...)` pauses.** DreamCarve's manual-spindle pauses are
  `M0 (MSG, ...)`. LinuxCNC and Mach3 show the message. UCCNC documents no
  `MSG`; RS274/NGC says messages "should be displayed" (3.3.4). Where the
  message is not shown, `export` still lists every pause.
- **Header modal codes.** `G40`, `G49` and `G80` only cancel modes
  DreamCarve never sets. `G91.1` selects incremental arc centres, which is
  how DreamCarve writes `I` and `J`. The safety pass accepts all four in
  any program, and `G90.1` in none (#154). Each line of the header is
  written again after every pause, with the units and WCS lines (#55).

Not used, and why:

- **`%`.** [O] "File Requirements": a percent line "is optional if the
  file has an M2 or M30 in it", and "an error will be signaled if a file
  has a percent line at the beginning but not at the end". The program ends
  with `M2`.
- **`M6`.** With `hal_manualtoolchange`, `M6` stops the spindle and "the
  dialog will stay active until the 'continue' button is pressed" ([TC]).
  Nothing documents jogging or touching off while it waits, and LinuxCNC's
  answer to a new bit's length is `G43` with a tool table ([M]
  `#mcode:m6`: "The tool length offset is not changed by M6, use G43 after
  the M6"). Without a tool changer component, the stepper configuration's
  HAL loops `iocontrol.0.tool-change` back to `tool-changed`
  (<https://linuxcnc.org/docs/stable/html/config/stepper.html#_standard_pinout_hal>),
  so `M6` returns at once and the program would cut with the old bit. And
  `T<n>` must be in the tool table. So no `M6`; one program per tool run.

### Changed from PureCutCNC

- **`O0001`.** Acceptance 36 and PureCutCNC open with `O0001

  after a subroutine label"; 10.8.7: "The O line may not have a line
  number (N word) on it"). The manual does not say what an `O` line at the
  start of the main program does. It is left out.
- **`M6`.** [MILL] 10.8.3: "Provided tool change requests are not to be
  ignored (as defined in Configure>Logic), Mach3 will call a macro M6Start
  ... It will then wait for Cycle Start". [CFG] 5.6.6.1 offers "Ignore Tool

  user can jog at the wait is not documented (6.2.7.2 allows jogging in a
  feed hold). So no `M6`.
- **`;` comments.** Not in either manual (10.5.5 documents `( )` and
  `//`). DreamCarve writes `( )` only.
